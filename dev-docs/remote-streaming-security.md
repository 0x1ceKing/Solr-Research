# Remote streaming attack surfaces in Solr 9.7.0

## Background
Remote streaming features (`stream.url`, `stream.file`, and `stream.body`) were made opt-in beginning with Solr 9.x; they no longer honor `solrconfig.xml` flags and instead are guarded by the `SOLR_ENABLE_REMOTE_STREAMING` / `solr.enableRemoteStreaming` and `SOLR_ENABLE_STREAM_BODY` / `solr.enableStreamBody` system properties or environment variables. Administrators are instructed to flip those switches when legacy clients depend on the parameters, which means new deployments may still expose the same attack surface as older vulnerable releases if those properties are set for compatibility.【F:solr/solr-ref-guide/modules/upgrade-notes/pages/major-changes-in-solr-9.adoc†L173-L177】

## 1. SSRF via `stream.url`
* **Root cause** – When `solr.enableRemoteStreaming` evaluates to `true`, `SolrRequestParsers.buildRequestFrom` walks every user-supplied `stream.url` value, instantiates `ContentStreamBase.URLStream` with a raw `java.net.URL`, and immediately queues that stream for processing without any allow-listing, scheme validation, or hop-by-hop filtering.【F:solr/core/src/java/org/apache/solr/servlet/SolrRequestParsers.java†L205-L237】
* **Trigger** – Any request handler that eventually calls `SolrRequestParsers` (e.g., `/select`, `/debug/dump`, many stream handlers) will dereference attacker-controlled URLs once the property is turned on. The built-in `TestRemoteStreaming` fixture demonstrates the behavior by pointing `stream.url` at another Solr endpoint to download CSV output.【F:solr/core/src/test/org/apache/solr/request/TestRemoteStreaming.java†L73-L105】
* **Impact** – An unauthenticated attacker on an instance where remote streaming has been enabled can:
  * pivot into the control plane (e.g., AWS/GCP metadata endpoints) and exfiltrate credentials (classic SSRF),
  * abuse Solr itself as a blind HTTP client to scan internal networks, and
  * coerce Solr into sending destructive HTTP verbs at arbitrary targets by pointing `stream.url` at an update handler URL that embeds `stream.body`, a pattern identical to CVE-2017-12629.
* **Why this is still a problem in 9.7.0** – Although the property is off by default, the code path has no additional guardrails compared to the vulnerable 6.x/7.x releases: there is no URL allow-list, the `ContentStreamBase.URLStream` constructor trusts DNS resolution, and the fetched bytes are immediately fed to downstream request handlers. Many operators enable `SOLR_ENABLE_REMOTE_STREAMING=true` via `bin/solr` (the script still exposes helper flags) for backwards compatibility, reintroducing the CVE-2017-12629 SSRF primitive.
* **Mitigation ideas** – Keep the property disabled, or add an allow-list (ideally reuse `AllowListUrlChecker`) before instantiating `URLStream`. Long-term, remote streaming should enforce protocol restrictions and treat update handler URLs as privileged destinations.

## 2. Arbitrary file disclosure via `stream.file`
* **Root cause** – The same `SolrRequestParsers.buildRequestFrom` method also loops over `stream.file` values and creates `ContentStreamBase.FileStream` for each entry, passing the attacker-supplied string straight into `new File(file)`. There is no canonicalization, path normalization, or sandboxing once `solr.enableRemoteStreaming` is true.【F:solr/core/src/java/org/apache/solr/servlet/SolrRequestParsers.java†L223-L237】
* **Trigger** – An attacker can issue a query such as `/select?q=*:*&stream.file=/etc/passwd&wt=xml` (or hit any handler reachable without authentication). As long as remote streaming is enabled, Solr will open that path on the filesystem and hand the contents to the handler, which typically echoes the bytes back in the response body.
* **Impact** – This revives the CVE-2017-12629/LPE class of bugs for modern Solr:
  * Arbitrary file read of any path that the Solr process can access (JKS trust stores, `solr.xml`, core properties, etc.).
  * Combination with `stream.body` enables write primitives – an attacker can pipe the contents of `/etc/shadow` into an update request and immediately index secrets for later retrieval, or feed shell scripts into `/update` to drop malicious configuration into the data directory.
  * Potential privilege escalation in multi-tenant clusters where trust boundaries rely on OS-level permissions.
* **Why this persists** – Disabling the parameters in `solrconfig.xml` is no longer effective, so old configuration files that accidentally left `<requestParsers enableRemoteStreaming="true"/>` in place do nothing. Operators now have to remember to *not* set the environment variable when upgrading; any automation that previously depended on those parameters is likely to re-enable them and unknowingly re-open unrestricted file system access.
* **Mitigation ideas** – Keep remote streaming disabled. If absolutely needed, wrap `stream.file` handling with `CoreContainer.assertPathAllowed` (like `/admin/file` already does) and require per-core allow-lists before touching the filesystem.
