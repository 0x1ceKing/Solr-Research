# Apache Solr 9.7.0 – Additional Vulnerability Candidates

## 1. SSRF primitive resurrected by disabling the URL allow list
* **Source** – The distributed request path reads the user-controlled `shards` parameter inside `HttpShardHandler.prepDistributed`. When Solr runs without ZooKeeper (classic mode) and the admin has not configured an explicit allow-list, `StandaloneReplicaSource.Builder` simply splits the attacker-provided comma/pipe-separated list into raw URLs. Those addresses get turned into outbound HTTP2 shard requests without any other vetting once the `AllowListUrlChecker` is disabled via the legacy compatibility system property (`solr.disable.url.allow-list` or `solr.disable.shardsWhitelist`).【F:solr/core/src/java/org/apache/solr/handler/component/HttpShardHandler.java†L250-L345】【F:solr/core/src/java/org/apache/solr/handler/component/StandaloneReplicaSource.java†L31-L76】【F:solr/core/src/java/org/apache/solr/security/AllowListUrlChecker.java†L100-L155】
* **Sink** – `HttpShardHandler` hands the resolved shard URLs directly to the load-balanced HTTP client, which connects to each URL and streams the response back into the original Solr response payload. There is no protocol filtering, so `http`, `https`, and even custom schemes accepted by the JVM URL handlers become reachable.
* **Trigger example** – With the allow list turned off for backwards compatibility (`bin/solr start -Dsolr.disable.url.allow-list=true`), a low-privileged user can hit the public search handler and pivot Solr into contacting internal metadata services: `/solr/gettingstarted/select?q=*:*&wt=json&shards=http://169.254.169.254/latest/meta-data/&shards.tolerant=true`. The shard fetch runs as the Solr JVM user, so any internal HTTP endpoint reachable from that network namespace becomes exfiltratable.
* **Prior art** – This is the same SSRF vector covered by CVE-2017-12629/CVE-2019-12409; the modern allow-list is the only thing preventing it. Disabling the allow list (which is still advertised in upgrade notes as a migration escape hatch) brings the bug pattern back unchanged.

## 2. Unauthenticated config and tlog disclosure via `/replication?command=filecontent`
* **Source** – `ReplicationHandler.handleRequestBody` immediately delegates to `getFileStream` when it sees `command=filecontent`. There is no authentication gate, so anyone who can reach the handler can request arbitrary files inside the core’s index (`file`), config (`cf`), or transaction log (`tlogFile`) spaces.【F:solr/core/src/java/org/apache/solr/handler/ReplicationHandler.java†L264-L311】【F:solr/core/src/java/org/apache/solr/handler/ReplicationHandler.java†L683-L758】
* **Sink** – `LocalFsConfFileStream.initFile` resolves the attacker-supplied `cf` parameter against `core.getResourceLoader().getConfigPath()` and streams the bytes back in raw form, only blocking absolute paths or path traversal segments. Sensitive files such as `security.json`, keystore passwords, or proprietary schema files are therefore directly exposed once replication is enabled for a core.【F:solr/core/src/java/org/apache/solr/handler/ReplicationHandler.java†L1515-L1759】
* **Trigger example** – A GET like `/solr/gettingstarted/replication?command=filecontent&wt=filestream&cf=security.json` dumps the entire security configuration even if the cluster otherwise enforces authentication on `/select`, because ReplicationHandler is still part of `solrconfig.xml` by default. Attackers can likewise enumerate index files via `file=segments_7` or steal replayable update logs via `tlogFile=tlog.0000000001`. If `security.json` stores BasicAuth hashes or PKCS12 passwords, this quickly snowballs into full cluster compromise.
* **Prior art** – This is the same unauthenticated file-disclosure surface referenced in CVE-2022-39135 and earlier replication bugs; Solr 9.7.0 still wires ReplicationHandler into the default example configs with no authz checks, so the root cause persists.

## 3. Backup APIs accept arbitrary filesystem paths
* **Source** – Every collection/core backup endpoint eventually calls `BackupAPIBase.getAndValidateBackupLocation`, which merely forwards the user-supplied `location` parameter into `BackupRepository.getBackupLocation` and then into the repository implementation with no sandboxing. The default `LocalFileSystemRepository` simply turns that string into a `Path` and starts reading/writing there via `Files.exists`, `Files.createDirectories`, `Files.newOutputStream`, etc., regardless of whether it points inside `solr.home`.【F:solr/core/src/java/org/apache/solr/handler/admin/api/BackupAPIBase.java†L42-L121】【F:solr/core/src/java/org/apache/solr/core/backup/repository/BackupRepository.java†L37-L86】【F:solr/core/src/java/org/apache/solr/core/backup/repository/LocalFileSystemRepository.java†L52-L139】
* **Sink** – `ListCollectionBackups` (and the corresponding V1 `/admin/collections?action=LISTBACKUP`) feeds the attacker-controlled location into `BackupFilePaths.buildExistingBackupLocationURI` and `repository.listAllOrEmpty`, disclosing directory listings and `backup.properties` from any readable path that the Solr OS account can touch. Likewise, the `BACKUP`, `RESTORE`, `INSTALLCOREDATA`, and `DELETEBACKUP` code paths will happily create/delete directories or stream Lucene files at that arbitrary location as root/Solr, letting a low-privileged API caller overwrite system files or populate a webroot with attacker-chosen data.【F:solr/core/src/java/org/apache/solr/handler/admin/api/ListCollectionBackups.java†L79-L112】【F:solr/core/src/java/org/apache/solr/handler/admin/api/CreateCollectionBackup.java†L83-L142】【F:solr/core/src/java/org/apache/solr/handler/admin/api/RestoreCore.java†L84-L130】
* **Trigger example** – Issue `curl 'https://solr.example/solr/admin/collections?action=LISTBACKUP&name=foo&location=/var/lib/solr/../../etc&wt=json'`. Even if the named backup never existed, the handler will traverse into `/etc`, enumerate files, and leak their metadata in the JSON response. Switching to `action=BACKUP` with `location=/var/lib/solr/../../var/www/html` causes Solr to create directories and drop index snapshots into the target, which can be weaponized as a primitive for arbitrary file write.
* **Why it matters** – The documentation still encourages operators to expose backup APIs to automated tooling. Without an allow-list, a compromised admin UI credential (or any code path with `COLL_EDIT_PERM`) instantly turns into local file read/write wherever the Solr account has permissions, which is much broader than the intended `<allowPaths>` sandbox.

## 4. Compatibility flag disables trusted-config authentication entirely
* **Source** – The config-set creation API is supposed to reject unauthenticated callers whenever they clone a “trusted” base config (i.e., one containing security or executable resources). That guard lives at the top of `CreateConfigSetAPI.create` and only runs when `ConfigSetsHandler.DISABLE_CREATE_AUTH_CHECKS` is false. The flag is wired directly to the legacy system property `-Dsolr.disableConfigSetsCreateAuthChecks`, which is still documented as a migration option in 9.x.【F:solr/core/src/java/org/apache/solr/handler/admin/ConfigSetsHandler.java†L58-L66】【F:solr/core/src/java/org/apache/solr/handler/configsets/CreateConfigSetAPI.java†L60-L86】
* **Sink** – When an operator sets the property (for example to preserve pre-8.x behavior), the trusted-config check is never evaluated and `runConfigSetCommand` blindly clones whatever base config name the attacker supplies. That includes `_default` and any curated configs that ship with `security.json`, request-handler plugins, or package references. Once a malicious actor can copy those into a new configset, they can upload arbitrary `solrconfig.xml`, register custom update processors, or drop a permissive `security.json`, then mount the configset on a new core via `/admin/cores` to seize unauthenticated control of the node.
* **Trigger example** – Start Solr with `-Dsolr.disableConfigSetsCreateAuthChecks=true` (or leave it in `solr.in.sh` from legacy installs). An unauthenticated HTTP client can then run `curl 'https://solr.example/solr/admin/configs?action=CREATE&name=hijacked&baseConfigSet=_default'` to clone the trusted `_default` configset. The attacker follows up with `action=UPLOAD` calls to replace `solrconfig.xml` or `security.json`, and finally `admin/cores?action=CREATE&name=owned&configSet=hijacked` to activate the tampered config without ever presenting credentials.
* **Impact** – This is an authentication bypass masquerading as “compatibility mode.” The code never warns administrators that setting the flag reintroduces CVE-2015-8797–style config hijacking, and the block still defaults to “off,” so a single misplaced JVM argument effectively disables authz on the entire config-set surface.

## 5. Admin UI query console executes CSV/txt responses as HTML
* **Source** – The Angular `QueryController` copies the user-selected `wt` parameter directly into `$scope.lang` for display purposes, falling back to JSON only when the user leaves `wt` empty. That happens inside `QueryController#doQuery` right after it receives the HTTP response.【F:solr/webapp/web/js/angular/controllers/query.js†L249-L257】  The response body is stored verbatim because the `Query` service’s `$resource` wrapper disables Solr’s JSON parsing and returns `{data: <raw body>}` for every response.【F:solr/webapp/web/js/angular/services.js†L233-L256】  When the admin selects a text-oriented writer such as `wt=csv` or `wt=python`, `$scope.lang` inherits that exact value.
* **Sink** – The query results template renders the server reply via `<code ng-bind-html="response.data | highlight:lang | unsafe">`, which trusts whatever comes out of the `highlight` filter.【F:solr/webapp/web/partials/query.html†L573-L577】  The filter returns the input string unchanged whenever `lang` is `txt` or `csv`, because it only runs Highlight.js for languages other than those two.【F:solr/webapp/web/js/angular/app.js†L202-L208】  Combined with Angular’s `$sce.trustAsHtml` (`unsafe` filter), any unescaped CSV body is dropped directly into the DOM.
* **Trigger example** – A low-privileged user (or even an external customer) inserts a stored payload by indexing a document with a field value like `<img src=x onerror=alert(document.domain)>` through whatever `/update` handler the deployment exposes: `curl 'https://solr.example/solr/gettingstarted/update?commit=true' -H 'Content-Type: application/json' -d '[{"id":"xss","payload":"<img src=x onerror=alert(document.domain)>"]'`. When an authenticated operator later inspects the collection via the Admin UI, sets the Query screen’s “wt” dropdown to `csv`, and runs `q=id:xss`, Solr streams the CSV row back exactly as stored. The UI’s `ng-bind-html` block interprets the `<img>` tag as DOM and runs the attacker’s JavaScript, letting the stored data exfiltrate the admin’s session or pivot into the browser.
* **Why it matters** – Many real deployments allow end users to index arbitrary strings (product reviews, log messages, etc.). Solr’s admin console is therefore reachable from untrusted content. By simply changing the response writer, an attacker can upgrade “stored data” into “stored XSS” without ever touching the UI code or filesystem.

## 6. File browser renders attacker-controlled config files without sanitization
* **Source** – The Files UI panel pulls arbitrary config files through the `/admin/file` request handler via the `Files.get()` resource, which hands the bytes straight back in `$scope.content` without any escaping or schema enforcement.【F:solr/webapp/web/js/angular/services.js†L222-L231】【F:solr/webapp/web/js/angular/controllers/files.js†L71-L89】  The handler (`ShowFileRequestHandler`) simply streams the requested file or ZooKeeper node back using the `RawResponseWriter`, so whatever is stored on disk or in ZooKeeper survives unchanged until it reaches the browser.【F:solr/core/src/java/org/apache/solr/handler/admin/ShowFileRequestHandler.java†L133-L205】
* **Sink** – The Files template emits `<code ng-bind-html="content | highlight:lang | unsafe">` when showing the selected file.【F:solr/webapp/web/partials/files.html†L21-L38】  As with the query console, the shared `highlight` filter does nothing (returns the raw string) whenever the inferred language is `txt` or `csv`. That is the default for most config artifacts (`lang` is derived from the extension; anything unknown falls back to `txt`). The `$sce.trustAsHtml` call in the `unsafe` filter therefore injects the untrusted file contents into the DOM.
* **Trigger example** – Any actor who can upload or edit a configset (for example via `curl -F file=@payload.zip 'https://solr.example/solr/admin/configs?action=UPLOAD&name=infected'`) places a file such as `conf/hack.txt` containing `<svg onload=alert(document.cookie)>`. The attacker convinces an administrator to open that configset in the Admin UI, navigate to **Files**, and click `hack.txt`. Because `FilesController` sets `lang` to `txt` for unknown extensions, the view prints the payload verbatim, immediately executing it in the admin’s browser. Even if `/admin/configs` itself is protected, any compromised core owner or ZooKeeper write path can weaponize the `/admin/file` browser to steal cookies or issue privileged Solr API calls via the victim’s session.
* **Pattern match** – This mirrors the historical CVE-2017-12629 admin-console XSS bugs: the UI continues to trust the response writers, so any path that lets untrusted parties drop files/config snippets effectively becomes a stored XSS primitive as soon as an operator inspects them.
